# TECHNICAL_NOTES.md

## 1. プロジェクト概要

### 1.1 目的

自作したTransformer文章生成モデルを，Web APIおよびWeb UIから利用できるようにする．モデルの実装だけでなく，Webサービス化，コンテナ化，クラウド環境へのデプロイまでを一通り経験することを目的とした．

### 1.2 技術スタック

| 領域         | 技術                       |
| ---------- | ------------------------ |
| モデル推論      | Python，自作Transformerモデル  |
| API        | FastAPI，Pydantic         |
| Web UI     | Gradio                   |
| コンテナ化      | Docker，Docker Compose    |
| コンテナ実行     | Singularity／Apptainer    |
| コンテナイメージ管理 | Docker Hub               |
| クラウド       | AWS EC2，Ubuntu 22.04 LTS |

### 1.3 全体構成

```text
自作Transformerモデル
        |
        v
  Generatorクラス
  ├── モデルのロード
  └── 文章生成処理
        |
        +-------------------+
        |                   |
        v                   v
     FastAPI              Gradio
   文章生成API           Web UI
    Port 8000            Port 7860
        |                   |
        v                   v
  Dockerイメージ       Dockerイメージ
        |                   |
        v                   v
      SIF形式             SIF形式
        |                   |
        +---------+---------+
                  |
                  v
               AWS EC2
          外部から動作確認
```

※APIとWeb UIは別プロセスとして実行する．それぞれのプロセスで`Generator`を初期化するため，モデルもそれぞれのプロセスでロードされる．

## 2. FastAPI・Gradioの実装

### 2.1 Generatorクラスによる処理の共通化

モデルのロード処理と文章生成処理を`Generator`クラスにまとめ，FastAPIとGradioの双方から利用できる構成とした．

主な処理は以下のとおり．

1. 実行デバイスを選択する（CUDAが利用可能ならCUDA，それ以外はCPU）．
2. 設定ファイルを読み込む．
3. トークナイザを初期化する．
4. 設定されたチェックポイントを読み込み，モデルに重みをロードする．
5. `generate()`から共通の文章生成処理を呼び出す．

モデルのロードはリクエストごとではなく，API・UIそれぞれのプロセス起動時に行う構成とした．

### 2.2 FastAPI

FastAPIでは，文章生成APIを実装した．

| エンドポイント     | メソッド | 役割                     |
| ----------- | ---- | ---------------------- |
| `/`         | GET  | APIの稼働確認用メッセージを返す      |
| `/generate` | POST | 入力されたプロンプトに基づいて文章を生成する |
| `/docs`     | GET  | API仕様の確認および対話的な動作確認    |

`POST /generate`では，Pydanticのリクエストモデルを利用して入力を受け取り，`Generator.generate()`を呼び出す．生成結果はJSON形式で返す．

主な入力パラメータ：

* `prompt`：生成の起点となる文章
* `max_new_tokens`：新たに生成する最大トークン数
* `temperature`：生成時の確率分布の調整
* `top_k`：次のトークン候補を上位K件に制限する設定

### 2.3 Gradio

Gradioでは，ブラウザ上から文章生成を試せるWeb UIを実装した．

主な入力項目：

* プロンプト
* 生成する最大トークン数
* Temperature
* Top-k

UIから入力を受け取る関数が`Generator.generate()`を呼び出し，生成結果を画面に表示する．

Gradioの起動ポートは7860とした．

### 2.4 APIとUIを分けた理由・構成上の特徴

APIとUIは別々に実装・起動し，それぞれのURLから利用できるようにした．GradioからFastAPIを呼び出す構成ではなく，両者が共通の生成処理を直接利用する構成である．

この構成により，API経由での利用と，ブラウザからの操作による利用をそれぞれ確認できる．一方，別プロセスで動作するため，モデルのロードやメモリ使用量はプロセスごとに発生する．

## 3. DockerからSIF形式への変換

### 3.1 Dockerによるコンテナ化

API用とGradio用にDockerfileを分け，それぞれのコンテナイメージを作成した．Docker Composeを使ってローカル環境で両サービスを起動し，動作確認を行った．

### 3.2 Docker Hubへの登録

作成したイメージをDocker Hubへ登録した．これにより，イメージを別の実行環境で取得して利用できるようにした．

### 3.3 SIF形式への変換

研究・HPC環境で利用されるSingularity／Apptainerを経験する目的で，DockerイメージをSIF形式に変換して実行した．

基本的な流れ：

1. Dockerイメージを作成する．
2. Docker Hubへイメージを登録する．
3. Singularity／Apptainerでイメージを取得し，SIF形式に変換する．
4. SIFファイルを実行し，APIとWeb UIの動作を確認する．

### 3.4 ネットワーク設定

通常実行に加え，`--net`によってネットワーク分離を有効にした実行も試した．この場合，コンテナ側のネットワークとホスト側のネットワークが異なるため，ホスト側からアクセスするにはポートマッピングなどの設定が必要となる．

実行例：

```bash
sudo singularity run \
  --net \
  --network-args "portmap=8000:8000/tcp" \
  transformer-text-gen-service_api.sif
```

Gradio側ではポート7860を使用する．

なお，WSL上でネットワーク分離を有効にした場合，コンテナ内からの`curl`ではアクセスできても，Windowsのブラウザからは接続できない事象があった．これはアプリケーション自体の起動失敗とは区別して考える必要がある．

## 4. AWS EC2へのデプロイ

### 4.1 実行環境

* インスタンス：AWS EC2
* OS：Ubuntu 22.04 LTS
* コンテナ実行環境：Apptainer
* APIポート：8000
* Gradioポート：7860

当初はAmazon Linux上へのSingularity導入を試みたが，インストール時の問題に対応できなかったため，Ubuntu 22.04 LTSに切り替えてApptainerを導入した．

### 4.2 デプロイ手順

1. EC2インスタンスを作成する．
2. SSHで接続し，Apptainerを導入する．
3. ローカルで作成したSIFファイルを`scp`でEC2へ転送する．
4. API用・Gradio用のコンテナを起動する．
5. セキュリティグループの設定を確認し，外部からアクセスする．
6. ブラウザとスマートフォンから動作確認を行う．

### 4.3 動作確認

以下を確認した．

* FastAPIの`/docs`へアクセスできること
* API経由で文章生成を実行できること
* GradioのWeb UIへアクセスできること
* 外部ブラウザおよびスマートフォンから利用できること

HTTPS化は未実施であり，HTTPでの動作確認までを実施範囲とした．

## 5. トラブルシューティング

トラブル対応では，エラー内容だけで判断せず，実行条件・ログ・ファイル配置・コンテナ構成を確認し，原因を切り分けてから修正した．

### 5.1 Apptainer実行時のパス問題

#### 発生した問題

ネットワーク分離を有効にして`sudo`でコンテナを実行した際，設定ファイルを参照できず，起動に失敗した．

#### 原因の切り分け

通常実行時と`sudo`・`--net`指定時の作業ディレクトリを`pwd`で比較した．

| 実行条件             | 確認された作業ディレクトリ |
| ---------------- | ------------- |
| 通常実行             | リポジトリのディレクトリ  |
| `sudo`・`--net`指定 | `/root`       |

作業ディレクトリが異なると，相対パスで指定した設定ファイルの参照先も変わる．`--pwd /code`を指定すると起動できたことから，作業ディレクトリの違いが問題に関係していると判断した．

#### 対処

実行時のカレントディレクトリに依存しないよう，Pythonファイルの配置場所を基準にプロジェクトルートを求めるよう変更した．

```python
ROOT_DIR = Path(__file__).resolve().parent.parent
```

これにより，設定ファイルのパスを実行時の作業ディレクトリに依存せずに指定できるようにした．修正後は`--pwd /code`を指定せずに起動できた．

#### 学び

* エラーが発生したときは，実行コマンドや実行環境の違いを比較する．
* 相対パスはカレントディレクトリに依存するため，設定ファイルやモデルファイルの参照では注意が必要．
* コンテナ内のファイルが存在することと，プログラムがそのファイルを正しいパスで参照できることは別問題である．

### 5.2 Gradioと依存ライブラリのバージョン不整合

#### 発生した問題

Gradioの起動時に以下のインポートエラーが発生した．

```text
ImportError: cannot import name 'HfFolder' from 'huggingface_hub'
```

#### 原因の切り分け

エラーメッセージを手掛かりに，Gradioと`huggingface_hub`の互換性を調査した．利用していたGradioが参照するAPIと，インストールされたライブラリのバージョンが合っていないことが問題だった．

#### 対処

関連パッケージのバージョンを調整し，以下の組み合わせで起動時エラーが解消した．

```text
gradio==3.50.2
huggingface_hub==0.19.4
transformers==4.30.2
pydantic==1.10.13
```

#### 学び

* ライブラリ単体の最新版を入れるだけでは，既存の依存関係と互換性が合わない場合がある．
* エラーメッセージを手掛かりに関連ライブラリの互換性を調べ，組み合わせで管理することが重要．
* 起動時エラーが解消したことと，すべての機能が正常に動作することは別なので，必要な機能の動作確認も行う．

### 5.3 コンテナイメージの肥大化

#### 発生した問題

Singularityの操作中にVS Codeの接続が不安定になり，作業継続に支障が出た．作成したSIFファイルのサイズを確認すると，API用が約9GB，Gradio用が約16GBだった．

#### 原因の切り分け

Gradio用イメージのビルド時に，先に作成したAPI用SIFファイルがビルド対象に含まれていることを確認した．

#### 対処

`.dockerignore`にSIFファイルを除外する設定を追加し，Gradio用イメージのビルド対象から不要ファイルを除外した．その結果，SIFファイルのサイズは約3GBとなり，VS Codeの接続不安定も解消した．

#### 学び

* Dockerのビルドコンテキストには，イメージに不要なファイルが含まれることがある．
* `.dockerignore`を使うことで，ビルド対象から不要なファイルを除外できる．
* 不要なファイルを除外することは，イメージサイズの削減だけでなく，ビルド効率や開発環境の安定性にも関係する．

### 5.4 Pythonモジュールのインポート問題

#### 発生した問題

コンテナ起動時に，以下のインポートエラーが発生した．

```text
ImportError: cannot import name 'JapaneseTokenizer' from 'data.tokenizer'
```

#### 対処

コンテナ内で`data/`や`utils/`をPythonから参照できるように，`PYTHONPATH`の設定を見直した．Docker Composeの環境変数に`PYTHONPATH=/code/app`を設定することで解消した．

#### 学び

Pythonのインポートは，モジュールの配置だけでなく，実行時の検索パスにも依存する．ローカル環境とコンテナ環境で検索パスが異なる場合，インポートエラーが起きることがある．
